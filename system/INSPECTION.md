# Publication inspection — Drive access and exact URL review

**Scope:** The manual inspection audits every catalogue resource with a `published_url`, including pending replacements and classroom slides. Generated-PDF publishing reuses the same inspector before upload, limited to the PDF's referenced resources and its existing target URL. Inspection is read-only; it never publishes, moves Drive files or changes catalogue metadata.

- **Any Google Drive / Google Docs URL:** verify the file ID, service-account access and non-Trash status using `files.get`. Use public `anyone` permissions from that response if available; otherwise try `permissions.list`. This is the same efficient path for owned and externally owned files, without guessing ownership.
- **Externally owned Drive files with hidden permission lists:** if existence was confirmed but public permissions remain unknowable, report NEEDS REVIEW. A human can open the exact public link as a viewer (ideally signed out), then record `human_reviewed_url` with the **exact current `published_url`**. Subsequent inspections pass this sharing check only while the URL stays identical. A confirmed private result is always FAIL, and inaccessible/unverifiable existence is still NEEDS REVIEW — human approval never overrides either or a missing/mismatching PDF checksum. If no publicly visible sharing metadata or permission listing exists, the inspector cannot reliably prove public access without a human test.
- **Generated PDF (has `pdf`):** after confirming public permissions, compare the official Drive file's `md5Checksum` with `pdf.approved_md5`. Missing approved/Drive checksum = NEEDS REVIEW; mismatch = FAIL. The first verified generated-PDF publication captures the baseline; never infer one from an unverified historical link.
- **Non-Drive URL:** exact matching `human_reviewed_url` passes. Otherwise require human review (NEEDS REVIEW). Approval is invalidated if the published URL changes.
- **Slides:** check the published presentation's Google URL; do not inspect its separately recorded `pdf_url` source or staged `holding_url` copy.
- **Unpublished resources:** skip if `published_url` is null.
- **Results:** PASS confirms the corresponding check; FAIL for confirmed bad/missing published links, private permissions or wrong generated PDF bytes; NEEDS REVIEW means uncertainty or pending human approval. Only FAIL makes the manually triggered full inspection workflow red. **Before generated-PDF upload, both FAIL and NEEDS REVIEW block release.** The release target's old approved checksum is intentionally excluded from that pre-upload check; the publisher verifies exact new bytes via post-upload Drive read-back.

The standalone manual Action summary shows a plain-language table of problems, links, and next steps (or one PASS row). Its separate downloadable JSON and .txt files retain technical details (sanitized API operation, file ID, status and reason), never raw exception bodies or credentials. The merge-release Action also presents a readable table instead of raw JSON, with the full release report in a separate artifact. The inspector never checks PDF hyperlinks, live site responses, ownership, folder placement or source content parity. A separate `publication_state.py` build compares current GitHub output with `pdf.approved_md5` to derive pending edits. The Drive publisher verifies exact bytes and writes the approved checksum/revision only after read-back.
